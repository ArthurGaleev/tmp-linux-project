# Project 1: метрики по журналу прослушиваний музыкального сервиса

Bash-скрипт `project1.sh` принимает CSV-журнал прослушиваний стримингового сервиса и выводит три характеристики.
Использованы только bash и стандартные утилиты (`tail`, `awk`, `sort`, `uniq`); других языков программирования в скрипте нет.
Идея - продолжение моего учебного проекта [Music-database](https://github.com/ArthurGaleev/Music-database) (PostgreSQL).

## Запуск

```bash
cd project1
./project1.sh listens.csv     # метрики
./check.sh listens.csv        # независимая проверка тех же метрик на SQL (sqlite3)
```

## Данные: `listens.csv` (~11,7 МБ, 120 000 событий)

Одна строка - одно прослушивание. Разделитель - запятая, первая строка - заголовок, кавычек и запятых внутри полей нет
(при генерации они заменяются пробелами).

| # | Поле | Смысл |
|---|------|-------|
| 1 | event_id | номер события |
| 2 | ts | время `YYYY-MM-DD HH:MM:SS` (01.09.2026 - 31.10.2026) |
| 3 | user_id | пользователь (3000 шт.) |
| 4 | country | страна пользователя, строчными буквами (8 стран) |
| 5 | song_id | номер песни (4800 шт.) |
| 6 | song_name | название песни |
| 7 | artist | первый исполнитель |
| 8 | genre | жанр (16 шт.) |
| 9 | device | `mobile`, `desktop` или `smart_speaker` |
| 10 | listened_sec | сколько секунд слушали |
| 11 | song_len_sec | длина песни в секундах |
| 12 | liked | 1, если поставлен лайк |

### Откуда данные

- **Каталог песен - реальный**: [Spotify Tracks Dataset](https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset)
  (названия, исполнители, жанры, длительности, популярность). Лицензия - [ODbL 1.0](http://opendatacommons.org/licenses/odbl/1.0/).
  Maharshi Pandya. (2022). Spotify Tracks Dataset [Dataset]. Kaggle. https://doi.org/10.34740/KAGGLE/DSV/4372070
- **Пользователи и события - синтетические**: сгенерированы SQL-скриптом `sql/generate.sql` (PostgreSQL) по схеме моей БД
  `sql/schema.sql`. Отличия этой схемы от репозитория Music-database помечены в `sql/schema.sql` комментариями `FIX` (исправление) и `NEW` (добавлено).
  Это не реальное поведение слушателей, а модель с заданными закономерностями (ниже).
- Исходный `dataset.csv` в репозиторий не кладется (`.gitignore`); `prepare_data.sh` скачивает его с Kaggle по API-токену
  (переменные окружения `KAGGLE_USERNAME`/`KAGGLE_KEY` или `KAGGLE_API_TOKEN`, либо `~/.kaggle/kaggle.json`) и запускает `psql -f sql/generate.sql`.
- `listens.csv` - производная база: содержит названия треков и исполнителей из каталога, поэтому распространяется на условиях ODbL с указанием источника выше.

### Модель генерации

| Что | Распределение |
|-----|---------------|
| Страны пользователей | usa 25, india 15, brazil 14, germany 12, japan 12, australia 10, france 8, sweden 4 (относительные веса) |
| Активность пользователя | экспоненциальная: мало «тяжелых» слушателей, много редких |
| Жанр | веса по стране: «мировые» жанры (pop, rock, hip-hop, edm, jazz, classical, country, heavy-metal) - 1, локальные - 0,2; для каждой страны усилены свои (japan: j-pop x5, india: indian x5, usa: country x4, germany: german x4 и т.д.) |
| Песня внутри жанра | закон Ципфа 1/rank^0,8 среди 300 самых популярных треков жанра |
| Время | 61 день равномерно; час суток с вечерним пиком (19-21 ч) |
| Устройство | mobile 55 %, desktop 30 %, smart_speaker 15 % |
| Скип (listened_sec < 30) | mobile 35 %, desktop 20 %, smart_speaker 10 %; Япония -5 п.п., Бразилия +3 п.п. |
| Не-скип | доля дослушивания ~ U(lo, 1), lo: mobile 0,55, desktop 0,70, smart_speaker 0,75; не меньше 30 с |
| Лайк | 8 % у не-скипов |

Параметры заданы в `sql/generate.sql`, генератор детерминирован (`setseed`).

## Что выводит `project1.sh`

Одна строка на значение, слова разделены пробелами; страны отсортированы по алфавиту.

1. `SKIP_RATE число` - доля прослушиваний короче 30 секунд, 4 знака после точки.
2. `TOPGENRE страна жанр число` - самый прослушиваемый жанр страны и число прослушиваний (при ничьей - жанр, первый по алфавиту).
3. `COMPLETION страна mobile desktop` - средняя доля дослушивания (`listened_sec / song_len_sec`, не больше 1) для устройств mobile и desktop; `NA`, если данных нет.

Пример вывода (сокращен):

```
SKIP_RATE 0.2683
TOPGENRE australia rock 2022
TOPGENRE brazil samba 3870
...
COMPLETION australia 0.5333 0.6959
COMPLETION brazil 0.5050 0.6695
...
```

### Как это устроено

- `tail -n +2` отбрасывает заголовок; `awk -F','` режет строку по запятой; условие `NF == 12` пропускает битые строки.
- Метрика 1: счетчики `total` и `skips` за один проход `awk`.
- Метрика 2: `awk` формирует пары `страна,жанр`, `sort | uniq -c` считает их, второй `awk` оставляет для каждой страны максимум.
- Метрика 3: ассоциативные массивы `sum[страна SUBSEP устройство]` и `cnt[...]`, в `END` печатается среднее.
- `LC_ALL=C` фиксирует порядок сортировки и формат чисел.
- `check.sh` сравнивает вывод `project1.sh` с теми же метриками, посчитанными SQL-запросами из `check.sql` (`sqlite3`).

## LLM (упрощено)

Использовалась LLM-модель Perplexity (ассистент с доступом к GitHub и веб-поиску); ниже краткая суть диалога.

1. Я приложил задание project1 и домашку linux4 и попросил придумать проект на основе моего репозитория Music-database. LLM прочитала задания и репозиторий и предложила журнал прослушиваний с тремя метриками (доля скипов, топ-жанр по странам, дослушивание mobile vs desktop) и два варианта реализации.
2. Я выбрал bash/awk для основных метрик и SQL (sqlite3) как проверочный вариант, PostgreSQL для генерации. Спросил, не лучше ли скачать готовый датасет. LLM сравнила Last.fm и Spotify Tracks и объяснила, что готовых данных со страной, жанром, устройством и длительностью нет, и предложила гибрид: реальный каталог треков + синтетические события.
3. Я согласился на гибрид, приложил датасет Spotify Tracks, указал лицензию и формат цитирования, попросил проверить мою БД на баги и не хранить датасет в репозитории, а скачивать по токену Kaggle. LLM написала `project1.sh`, `check.sh`/`check.sql`, `sql/schema.sql` (с исправлениями), `sql/generate.sql`, `prepare_data.sh` и сгенерировала `listens.csv`; результат `awk` и SQL-проверки совпал.
4. Я попросил убрать из README служебные пометки и упростить текст; LLM обновила README.
